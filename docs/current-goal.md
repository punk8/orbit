# 当前目标：产品可用

日期：2026-05-24

Orbit 接下来的设计和开发目标是从“工程骨架可运行”推进到“产品可用”。后续所有 UI、数据链路、权限治理、AI provider、测试和文档决策，都应优先服务这个目标。

如果开启新的 Codex goal 模式线程，请先使用 [Codex Goal 模式启动说明](goal-mode-launch.md) 中的启动 prompt 和验收边界。

## 目标定义

产品可用不是逐像素复刻 `assets/product-vision`，而是让一个可信的本地优先工作上下文产品真正能被 dogfood：

- 用户打开 Orbit 后，能快速知道今天发生了什么、哪些事项值得注意、证据来自哪里。
- Activity 能还原工作现场，并能从摘要跳回来源事件、OCR、截图或其他证据指针。
- Knowledge 和 Review Queue 能让用户高效审阅、编辑、确认、拒绝和归档上下文总结。
- Memory 能沉淀少量稳定、可追溯、可治理的长期记忆，而不是堆积原始记录。
- Recommendation 能给出有依据、置信度和建议动作的提醒，且默认不执行外部副作用。
- Handoff 能生成 Agent-safe 的 Markdown/JSON 上下文包，默认排除未确认、不可导出和 raw 私密内容。
- Sources 和 Settings 能清楚说明 Orbit 读了什么、保存了什么、允许什么、禁止什么，以及如何暂停、清理和删除。

## 当前差距判断

最新代码已经具备页面骨架和部分真实链路，但整体仍偏“工程控制台 / 可追溯调试界面”。`assets/product-vision` 代表目标产品感：更强的扫读效率、更明确的状态表达、更可信的证据治理、更完整的审阅和交接工作流。

后续开发不应只补底层能力，也不应只做静态视觉美化；优先把真实可用的端到端工作流做顺：

1. Today 产品化首页：真实活动、来源状态、知识草稿、建议和下一步行动能一屏扫读。
2. Activity 证据浏览：时间线、证据索引、事件流、来源策略和原始数据状态能互相跳转。
3. Knowledge / Review 审阅工作台：总结内容、Markdown 预览、证据、确认/拒绝/归档形成闭环。
4. Handoff 交接包：Today/Project 范围、安全边界、包含/排除理由、Markdown/JSON 预览完整可见。
5. Memory 治理：候选、确认、版本历史、有效期、证据和 Agent 上下文注入边界清楚。
6. Sources / Settings 治理控制台：权限、保留、AI 使用、Agent 导出、受保护应用和危险操作可解释。

## 设计原则

- 以用户任务为中心，不以数据库表、pipeline 阶段或 debug 字段为中心。
- 每个关键结论都必须能回到来源证据；没有证据的内容只能作为草稿或低置信提示。
- 默认中文可用，英文技术字段只在必要时出现，并优先转成用户能理解的文案。
- 默认本地优先、隐私优先、只读优先；任何副作用动作都必须明确授权。
- UI 要服务扫读和审阅效率：状态、置信度、敏感度、来源、下一步动作要比内部 ID 更显眼。
- 不再把 fixture 演示体验当作产品完成度；fixtures 只用于测试和安全样例。
- 如果一个实现只增加能力但没有改善用户完成工作流的能力，默认降低优先级。

## 验收口径

一个 checkpoint 只有在同时满足以下条件时，才算朝“产品可用”前进：

- 能用最新打包的 desktop app 手动走通对应用户工作流。
- 关键页面不只是空态或调试态，至少有真实或安全样例数据支撑可理解体验。
- 用户能看到来源、证据、状态、限制和下一步动作。
- `pnpm typecheck`、`pnpm test`、`pnpm lint` 或该 checkpoint 对应验收命令已运行并记录结果。
- 没有扩大默认采集范围、默认 raw 存储、默认外部 AI 发送或默认 Agent 导出。
